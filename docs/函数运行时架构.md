# 函数运行时架构：从「只会跑 JavaScript」到可插拔的多语言执行层

> 对应版本 `1.13.0-studio`。本文先分析旧实现的结构性问题，再说明重构后的分层、协议与扩展方式；
> 操作层面（怎么建函数、怎么切语言）见 [使用指南 §7](./使用指南.md)。

## 1. 旧实现长什么样

### 1.1 调用链

```
POST /v1/functions/:id/executions
        │
        ▼
store.executeFunction()                 ← 组装 ctx（databases/storage/users/env/meta）
        │
        ▼
runtime.executeFunctionCode(code, ctx, timeout)
        │
        ├─ worker_threads + SharedArrayBuffer + Atomics.wait   ← 默认
        └─ vm.runInContext                                     ← 降级（FUNCTION_ISOLATION=vm）
```

数据访问留在主线程，worker 通过同步 RPC 回主线程查 SQLite —— 这一层设计是对的，问题出在它上面。

### 1.2 四个结构性问题

**① `runtime` 字段是装饰品。** `functions.runtime` 从建表就有，创建时写死 `node-22`，执行时却完全没人读。控制台上写着「Runtime」，实际只有一条路。

**② 沙箱 API 被抄了两份。** `src/sandbox.ts`（vm 降级）和 `src/function-worker.mjs`（worker 主路径）各自维护一份 `transpile`、`ALLOWED_MODULES`、`console`、`res`、`require`。注释里写着「改动需同步」——靠注释同步的代码，迟早不同步。

**③ 语言假设散落在四层。** `store.createFunction` 默认 `entrypoint='src/main.js'`；`FunctionDetail` 把 `language="javascript"` 写死在编辑器上；创建弹窗的模板是前端常量；错误文案直接说「export default function」。加一门语言要改 6 个文件，还得记得改前端。

**④ 执行记录不记运行时。** 函数从 Node 切到 Python 之后，历史记录里的耗时、日志、响应无法解释——不知道当时跑的是哪个引擎。

除此之外，还有两个具体的能力缺口：入口文件不能按语言变化；运行时是否可用（比如机器上没装 Python）要到执行时才炸，而且报的是一句 `spawn ENOENT`。

## 2. 重构目标

| 目标 | 落地方式 |
|---|---|
| 语言由运行时决定，而不是由执行器决定 | `RuntimeDefinition` 携带 language / extension / entrypoint / templates |
| 执行器可插拔，协议与语言无关 | 进程内引擎 + 子进程桥 `studio-bridge/1` |
| 新增语言不改上层 | `runFunction()` 只认接口；注册表在启动时装配 |
| 运行前就知道能不能跑 | `GET /v1/runtimes` 返回 availability（解释器路径 + 版本） |
| 历史可追溯 | `executions.runtime` 记录每次实际使用的运行时 |
| 旧数据不炸 | 启动迁移归一历史 `runtime` 值，读写都做别名解析 |

## 3. 新分层

```
server/src/functions/
├── types.ts              # ExecContext / ExecutionOutcome / RuntimeDefinition（无语言细节）
├── registry.ts           # 注册表、别名归一、可用性探测（60s 缓存）、内置两门语言
├── index.ts              # runFunction()：唯一执行入口
├── engines/
│   ├── javascript.ts     # worker_threads 编排 + vm 降级
│   ├── javascript-worker.mjs
│   ├── vm.ts             # vm 沙箱（仅降级路径使用）
│   └── subprocess.ts     # 语言无关的子进程桥（stdio JSON 帧）
└── harnesses/
    └── python.ts         # Python harness 源码（每次执行写入临时目录）
```

上层只需要：

```ts
const outcome = await runFunction({
  runtime: fn.runtime, code: fn.code, entrypoint: fn.entrypoint,
  timeout: fn.timeout, env: fn.env, ctx,
});
```

`runFunction` 做三件事：解析并校验运行时（未知/不可用 → 400）、按入口文件执行、把 `runtime` 附回结果。至于底层是线程、进程还是将来的容器，调用方不需要知道。

### 3.1 内置运行时

| id | 语言 | 入口 | 引擎 | 协议 | 隔离手段 |
|---|---|---|---|---|---|
| `node-22` | JavaScript (ESM) | `src/main.js` | worker 线程，失败降级 vm | `studio-worker/1` | 独立 V8 isolate + `terminate()` + 256MB heap |
| `python-3` | Python 3 | `main.py` | 子进程 `python3 -I -B` | `studio-bridge/1` | 独立 PID + `SIGKILL` + rlimit + 网络守卫 |

Python 的版本号在探测时读取（`python3 -V`），所以同一份代码在 3.11 / 3.12 上都能显示真实版本。

### 3.2 为什么 Python 不做「进程内嵌」

CPython 没有安全的同进程中断手段：`PyThreadState_SetAsyncExc` 对阻塞在 C 扩展里的代码无效，子解释器也共享 GIL。要保证「死循环能被收掉」，进程是唯一可靠边界。代价是一次冷启动（实测中位数 70ms），换来的是超时必达、内存可控、崩溃不带走主进程。

## 4. `studio-bridge/1` 协议

### 4.1 时序

```
主进程                                   子进程（harness + 用户代码）
  │  spawn(cwd=临时目录) ─────────────────▶│
  │                                        │ 读 studio_request.json（req/meta）
  │                                        │ 加载 main.py，调用 handler(ctx)
  │◀── {"t":"log","level":"log","line":…} ─│ print() / ctx.log()
  │◀── {"t":"rpc","id":1,"ns":"databases", │ ctx.databases.list_documents(...)
  │      "method":"listDocuments",         │   ↑ 阻塞在 stdin.readline()
  │      "args":["products",{"limit":2}]} ─│
  │─── {"id":1,"value":{...}} ────────────▶│
  │◀── {"t":"result","status":200,         │ 返回 / 抛异常
  │      "headers":{},"body":{...},        │
  │      "failure":null} ──────────────────│
  │  SIGKILL 进程组 + 删临时目录            │
```

- **一行一个 JSON 帧**，`\n` 分隔；用户直接写 fd 1 的脏数据会被当成日志，不会打断协议。
- **RPC 是同步的**：主进程用 better-sqlite3 同步查询，查完立刻回一行。这样 Python 侧的 `list_documents()` 也是同步取值，与 Node 版语义一致，不需要 async/await 传染。
- **日志实时回传**：harness 把 `sys.stdout` 换成一个按行发送 `log` 帧的 writer，长任务不用等结束才看到输出。
- **结果单帧返回**：`status / headers / body / failure`，由 harness 统一序列化，`default=str` 兜底不可序列化对象。

### 4.2 超时、内存与清理

| 项目 | 做法 |
|---|---|
| 超时 | 主进程 `setTimeout` → `process.kill(-pid, SIGKILL)` 杀整个进程组（子进程 `detached`） |
| 内存 | harness 启动时 `RLIMIT_AS = STUDIO_MEMORY_MB`（默认 256MB） |
| CPU | `RLIMIT_CPU = timeout + 2`，防止绕过 wall-clock |
| 句柄 | `RLIMIT_NOFILE = 256` |
| 日志 | 最多 2000 行 / 512KB，超出追加 `[log output truncated]` |
| 响应 | 单帧上限 8MB，超限直接判失败而不是撑爆主进程 |
| 临时目录 | 每次执行 `mkdtemp`，结束/失败/超时都 `rm -rf`（实测无残留） |

### 4.3 Python 侧的对象模型

```python
def handler(ctx):
    print("hello")                                   # → log 帧
    docs = ctx.databases.list_documents("products", {"limit": 5})  # → 同步 RPC
    ctx.log("loaded", docs["total"])
    return ctx.res.json({"count": docs["total"]})
```

- `ctx.req` / `ctx.meta` / `ctx.env` 是 `dict` 子类，`ctx.req.method` 与 `ctx.req["method"]` 都能用；
- `databases` 同时提供 `snake_case` 与 JS 同名方法（`list_documents` / `listDocuments`），方便从 Node 迁移；
- `async def handler` 会被 `asyncio.run` 等待，同步函数直接调用；
- 返回非 `None` 且没有显式 `res` 时，返回值即响应体。

## 5. 扩展：加一门语言

### 5.1 最小步骤

1. 写一个 harness：从 stdin 读 RPC 回包、向 stdout 写帧、把用户文件当模块加载（参考 `harnesses/python.ts`，约 60 行有效代码）。
2. 在 `registry.ts` 里 `registerRuntime({...})`，给出 `probe()` 与 `execute()`。
3. 若解释器不在 PATH，用环境变量指定（如 `STUDIO_PYTHON_BIN`）。

```ts
registerRuntime({
  id: 'ruby-3',
  label: 'Ruby 3',
  language: 'ruby',
  version: '3.x',
  extension: 'rb',
  entrypoint: 'main.rb',
  protocol: 'studio-bridge/1',
  color: '#cc342d',
  templates: [{ id: 'hello', label: 'Hello world', description: '…', code: 'def handler(ctx)\n  ctx.res.json({ ok: true })\nend\n' }],
  probe: () => probeCommand(process.env.STUDIO_RUBY_BIN || 'ruby', ['-v']),
  execute: (input) => executeViaBridge({ id: 'ruby-3', command: 'ruby', args: ['harness.rb'],
    extension: 'rb', harnessName: 'harness.rb', harnessSource: RUBY_HARNESS, memoryMb: 256 }, input),
});
```

Ruby harness 的核心循环与 Python 完全同构：

```ruby
require 'json'
$stdout.sync = true
seq = 0
def emit(frame) = ($stdout.puts(JSON.generate(frame)); $stdout.flush)
def rpc(ns, method, args)
  seq += 1
  emit({ t: 'rpc', id: seq, ns: ns, method: method, args: args })
  msg = JSON.parse($stdin.gets)
  raise msg['error'] if msg['error']
  msg['value']
end
# 加载 main.rb 里的 handler(ctx)，捕获异常后 emit({t:'result', failure: e.message})
```

控制台不需要任何改动：`GET /v1/runtimes` 会自动多出一项，创建弹窗、语言高亮、切换运行时的逻辑都按 `language` 字段走。唯一要补的是 CodeMirror 的语言包（没有就退回纯文本）。

### 5.2 不该做的事

- 不要在 `store.ts` 里 `if (runtime === 'python')`：那就是回到重构前。
- 不要把数据库连接搬进子进程：单写连接、项目隔离、事件广播都在主进程，桥接是为了守住这一点。
- 不要把「可用性」当成执行期错误：创建时就该 400，让用户在保存前知道。

## 6. 数据模型与 API

### 6.1 迁移

启动时执行（`db.ts`，幂等）：

```sql
ALTER TABLE executions ADD COLUMN runtime TEXT;           -- 历史执行补一列
ALTER TABLE functionVersions ADD COLUMN runtime TEXT;     -- 版本也要记住「当时用什么跑」
ALTER TABLE functionVersions ADD COLUMN entrypoint TEXT;
UPDATE functions SET runtime='node-22'
  WHERE runtime IS NULL OR runtime='' OR lower(runtime) IN
    ('node','nodejs','node-18','node-18.0','node-20','node-20.0');
UPDATE functions SET runtime='python-3'
  WHERE lower(runtime) IN ('python','python3','py','python-3.10','python-3.11','python-3.12','python-3.13');
UPDATE functions SET entrypoint='main.py'
  WHERE runtime='python-3' AND (entrypoint LIKE '%.js' OR entrypoint='');
```

刻意不用 `LIKE 'node-%'`：将来加 `node-24` 时不会被这条语句改掉。

### 6.2 别名

读写两侧都归一（`registry.normalizeRuntimeId`）：`node` / `nodejs` / `js` / `node-18` / `node-20` → `node-22`；`python` / `py` / `python3` / `python-3.11` → `python-3`。旧脚本、旧 SDK、旧数据都能继续用。

### 6.3 HTTP

| 方法 | 路径 | 变化 |
|---|---|---|
| GET | `/v1/runtimes` | 新增：运行时清单 + 可用性 + 模板 |
| POST | `/v1/functions` | 新增校验：未知或本机不可用的运行时 → 400；入口/模板随语言取默认 |
| PATCH | `/v1/functions/:id` | 支持 `runtime`；切换语言时同步入口，初始模板自动翻译 |
| GET | `/v1/functions/:id` | 响应新增 `runtimeInfo`（含 availability） |
| POST | `/v1/functions/:id/executions` | 响应新增 `runtime`；执行记录落库 |

`GET /v1/runtimes` 的单项形状：

```json
{
  "id": "python-3", "label": "Python 3", "language": "python",
  "version": "3.x", "extension": "py", "entrypoint": "main.py",
  "protocol": "studio-bridge/1", "color": "#3b82f6",
  "availability": { "available": true, "binary": "python3", "version": "3.11.1" },
  "templates": [{ "id": "hello", "label": "Hello world", "description": "…", "code": "def handler(ctx): …" }]
}
```

## 7. 控制台

- **创建函数**：语言卡片（Node.js 22 / Python 3，显示真实版本与协议），模板下拉随之切换，预览直接是目标语言。
- **详情页**：`main.py` 用 Python 高亮；右上角显示 `Python 3 · 3.11.1`；概览里的运行时是带色点的 chip。
- **设置**：可切换运行时。手写代码原样保留；如果代码还是初始模板，会换成新语言的同名模板（避免 `main.js` 里躺着 Python）。
- **函数列表**：运行时列显示语言色点 + 名称，不再是一个无意义的字符串。

## 8. 安全边界（重要）

这是**进程级隔离**，不是容器级安全边界。当前做到：

- 不继承宿主环境变量：子进程只拿到 `PATH/LANG/HOME/TMPDIR` + 函数自己的变量，`STUDIO_SECRET_KEY` 之类不会泄漏；
- 函数变量不能覆盖 `STUDIO_ENTRYPOINT/TIMEOUT/MEMORY_MB`（系统变量在展开用户变量之后写入）；
- Python 侧屏蔽 `socket.connect` / `create_connection` / `getaddrinfo`，出网直接报「network access is disabled」；
- `rlimit` 限制地址空间、CPU、句柄数；
- 入口路径过滤 `..`，只允许临时目录内最多两层子目录。

没做到、也不打算在演示项目里做到的：

- 容器 / namespace 隔离、只读根文件系统、seccomp；
- 阻断 `ctypes`、`fork`、写文件等本地能力（进程内仍可写临时目录）；
- 依赖安装（`pip install` / `npm install`）——需要网络与包管理，属于部署期能力。

结论：**多租户生产环境请把 `executeViaBridge` 的 spawn 换成容器运行时**（Docker / Firecracker / gVisor），协议与上层代码不用动；当前的 rlimit + 网络守卫只适合「自己人写的函数」。

## 9. 性能

单次执行（本机，SQLite 本地盘，8 次取中位数）：

| 运行时 | 中位耗时 | 主要成本 |
|---|---|---|
| Node.js 22 | 47.5 ms | worker 启动 + ESM 转译 |
| Python 3.11 | 70 ms | 解释器冷启动 + harness 加载 |

Python 的固定开销约 30–40ms，适合短任务；长任务里占比可以忽略。两条路径都不复用进程/线程（每次执行独立），换来的是「上一次执行留下的状态绝不会影响下一次」。

## 11. 已知取舍

- **单文件**：一次执行只有一个入口文件。多文件需要把 `functionVersions.code` 扩成文件树，属于下一轮。
- **无依赖管理**：Python 只能用标准库；需要第三方包时应在镜像里预装，而不是运行期 `pip install`。
- **模板翻译只认内置模板**：用户改过的代码不会被改写，这是有意的——宁可切过去跑失败，也不悄悄替换业务逻辑。
- **Windows 的进程组语义不同**：`detached + kill(-pid)` 在 Windows 上退化为 `child.kill()`，孙子进程可能残留；生产部署按 Linux 设计。
